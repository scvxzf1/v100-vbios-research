| 项目 | 实际值 |
|---|---|
| 系统 | Ubuntu 24.04.5 LTS；内核 6.8.0-136-generic；X11 |
| GPU | Tesla V100-SXM2-16GB，GV100 / Volta |
| PCI | 0000:04:00.0；10de:1db1；/dev/nvidia1 |
| 驱动 | 580.178.04，闭源内核模块（modinfo license: NVIDIA） |

Applications Clocks 的 1312 MHz 不等于实际频率必然被锁在 1312 MHz。本机采样已有 1530 MHz；此前工作区张量探针报告也记录了 1530 MHz。提高 application clocks、锁频、提高功耗与扩大最高频率表是不同操作。

GPU 选择应使用 PCI BDF 或 UUID；本机 CUDA ordinal 与 nvidia-smi 索引顺序不同。另一张卡为 GTX 1050。

## 3. 参考 ROM 镜像边界

下列区间为文件物理偏移，右端不包含在区间内。

| 起点 | 终点 | 类型 |
|---|---|---|
| 0x000A00 | 0x00EE00 | Legacy PCIR，code type 0x00 |
| 0x00EE00 | 0x01FC00 | EFI PCIR，code type 0x03 |
| 0x01FC00 | 0x030800 | NPDS，code type 0xE0 |
| 0x030800 | 0x03DC00 | NPDS，code type 0xE0 |
| 0x03DC00 | 0x03E800 | NPDS，code type 0x70 |
| 0x03E800 | 0x04E400 | NPDS，code type 0x70 |

前五个镜像按头部长度取区间的加法 checksum 为 0，最后一个为 20；该类型可能具有不同尾部/签名约定，不能仅据此宣告完整 ROM 损坏。

笔记的固定 253440 字节（0x3DE00）裁剪点，比本 ROM 最后 E0 镜像终点 0x3DC00 多 512 字节，落在后续 type 0x70 镜像内部。0xE0 是 NPDS 头中的 code type，不是文件末字节的终止标记。现有 Turing e0-end 导出会修 last-image flags 和 checksum；这套处理并未在本卡/Volta Linux 上验证。

## 4. 表结构定位结果

BIT 位于 0xBB0；P token v2 数据在 0xCBE，C token v2 数据在 0xC63。本文的 raw pointer 是表内存储指针，physical offset 是文件物理偏移；两者必须经镜像映射转换。

### 功耗表：结构确定，Volta 控制语义仍需验证

- BIT P+0x2C：raw 0x21071 → physical 0x32871。
- 头部：version 0x30、header size 0x27、entry size 0x36（54 字节）、count 0x14（20 行）。
- header+0x0A 指定 TGP index=2，对应 row 起点 0x32904。
- row+2：100000 mW；row+6：300000 mW，文件偏移 0x3290A；row+10：300000 mW，文件偏移 0x3290E。
- 笔记列出的 0x32A89 一带，在本 ROM 为零，不能照写。

已确认结构定位并不等于已确认上机改写效果；本 ROM 的 power channel class 也不同于编辑器已审阅的 Turing 总板功耗布局。

### Performance / Base Clock：避免混称

- BIT P+0：Performance v0x50，physical 0x30955，表结束 0x30A5B。
- 其中 active row 的 clock0 子项包含 382（0x017E）@0x30A23；结构位置可定位，但不能据此宣称它就是 Supported Clocks 的全局上限。
- BIT P+0x38：Base Clock v0x20，physical 0x30A5B，结束 0x30C07，恰接下一表。
- row0 / row2 的第一个子项分别在 0x30A6E / 0x30AC0：1312，其后值为 328。
- row1 / row3 的对应子项分别在 0x30A97 / 0x30AE9：0x85FA（低14位=1530），其后值为 382。
- 382×4=1528，故不能将所有字段简单定义为精确的“MHz/4”；舍入、标志位及驱动解释需要单独追踪。

### VFE：笔记所称两个立即数尚无结构依据

- BIT P+0x20 指向 physical 0x314F5。
- 本 ROM 头部对应 15 个 25 字节变量及 150 个 24 字节方程；方程区间 0x31673..0x32483，后面紧接 Power Sensor 表。
- 该 VFE 表中没有 1530 的 little-endian u16 字节序列。
- 0x383F3 / 0x38741 处确有 1530 数值，但远在 VFE 表之外；周围呈指令状数据。未定位容器和指令语义前，不能称其为 VFE 频率截断立即数，更不能仅按数值替换。

## 5. Linux 加载路径

### 已排除直接套用的路径

1. 当前 Linux Vix Loader 通过开源内核模块把 payload 地址和长度交给 GSP 的 vbiosOverrideArgs 接收端，要求 R615，公开支持范围不含 Volta。
2. NVIDIA 开源模块从 Turing 起支持；更换为开源模块不能解决本机 Volta 的加载问题，另一张 Pascal GTX 1050 同样不在范围内。
3. `EnableGpuFirmware=0x11` 的公开定义是 ENABLED(1) | ALLOW_FALLBACK(0x10)，即尝试启用 GPU firmware 并允许失败回退。单独设置它不提供 VBIOS 文件或二进制数据，也不是通用的 Volta 覆盖开关。
4. NVML/NV-CONTROL 当前暴露的核心 offset 范围为 0–0；常规 offset 路线没有提供超过 1530 的空间。

### 新发现：Linux 580 闭源 RM 存在候选 host registry 读取路径

通过对本机精确版本 `/lib/modules/6.8.0-136-generic/updates/dkms/nvidia.ko` 的只读字符串与反汇编定位，发现不能再简单断言“Linux 完全没有 VBIOS registry 入口”：

- 函数 `_nv059933rm`（`.text` 约 0x284050，大小约 4335）读取字符串 `vbios`。
- 在约 0x284648 处分支将 `pGpu`、键名 `vbios`、缓冲区和长度传给 `_nv049785rm`；该 wrapper 将 `pGpu+0x9d8` 的 registry 对象传入 `_nv000819rm`，后者按 binary 类型查找 registry entry，复制 entry 数据并返回长度。这是实际 binary registry read，不是日志字符串。
- 另一函数 `_nv030843rm`（约 0x62fa90）读取另一份 `vbios` 字符串，并调用 `_nv049786rm`；该 DWORD-read wrapper 先查 DWORD，找不到时可按 binary entry 取前 4 字节，binary 长度大于 3 即返回成功；成功后设置 `pGpu+0x994=1`。随后 `_nv059933rm` 检查这个状态再走 binary read。
- `_nv059933rm` 成功读取后检查长度至少 512 且不超过初始缓冲容量，随后可能处理 `vbios000...` 分块；在约 0x284fe5 将 source 标记设为 2，再把 buffer/size 写入 `OBJVBIOS` 的约 `+0x2e8/+0x2f0`，并调用后续解析/校验路径（约 0x27ee50、0x27f510）。
- 这看起来像一个真正的 host-RM VBIOS registry override 候选路径，且不同于 GSP 的 `vbiosOverrideArgs`。但尚未确认：是否对 GV100 分支启用、完整键名/分块格式、镜像是否必须为当前卡版本、签名/校验规则、读取时机，以及能否在已初始化 GPU 上生效。
- 已确认的 Linux procfs 写入口 `/proc/driver/nvidia/gpus/0000:04:00.0/registry` 能写 binary registry；当前该文件只读显示 `Binary: ""`。截至本记录没有向其写入数据。
- 重要：本机正在运行的 VBIOS 是 88.00.4F.00.09，而用户提供的参考 ROM 是 88.00.18.00.01；不能用后者做第一份 live override 测试。

这条路径目前是“静态分析得到的候选”，不是已验证的操作方法。任何猜测的 key、分块格式或写入顺序都可能导致驱动拒绝 VBIOS、GPU 初始化失败或需要重启恢复。

## 6. 实验顺序与成功判据

1. 取得本机 88.00.4F.00.09 的真实只读 ROM 备份，核对 PCI、板卡信息、版本、完整长度和 hash。先做跨版本表结构比较。已尝试用普通权限运行 `nvidia-debugdump --dumpall --device 1`，因权限不足返回错误；随后通过 `su -c` 重试，认证仍失败，未得到有效转储。清理了本次生成的空 ZIP。当前仍未取得运行中 88.00.4F.00.09 的只读 ROM。
2. 完成 580.178.04 闭源模块的静态调用路径定位，确认 `vbios`、`vbios000...` 的完整命名、分块规则、读取时机和后续校验。当前不构造 ioctl，不写 registry。
3. 如建立入口，先加载未修改的本卡镜像并验证回读一致性及运行正常，避免同时引入跨版本 ROM 和参数修改。
4. 再采用小幅核心上限实验，例如研究 1560 MHz 档位，而不是直接复制 1700 MHz / 400 W。初始保持原功耗上限，不主动提高电压上限。
5. 分开验证：运行时确实使用目标镜像；最高频率枚举改变；负载实际频率连续超过 1530；同条件吞吐随之变化；数值正确性、ECC、Xid、功耗、温度正常。只看到名称、最大值或命令返回成功不算完整成功。
6. 若 Linux host override 路径最终不可用，后续属于闭源 RM/PMU 接口逆向或内核接口改造，不能用现有 Vix Loader 参数代替。
