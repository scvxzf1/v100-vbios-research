# V100 / NVIDIA 580.178.04：vbios 分块与初始化时序静态证据

日期：2026-10-25（只读静态分析）
对象：`/lib/modules/6.8.0-136-generic/updates/dkms/nvidia.ko`
源码：`/usr/src/nvidia-580.178.04`
范围：不发 ioctl，不做 live registry 写入，不改硬件或系统设置。

## A. `_nv059933rm` 的 `vbios000` 分块规则

### A.1 初始容量与基础读取

- 函数入口：`_nv059933rm = 0x284050`。
- `0x28406a` 从第二参数对象 `+0x158` 取函数指针；`0x284084` 经 `__x86_indirect_thunk_rax` 间接调用；返回值在 `0x284097` 保存为栈变量 `C`（`[rbp+0xc]`）。
- 因实际虚函数目标未解析，初始容量 `C` 的数值未知；不可推断为固定 64 KiB、128 KiB 等。
- `0x28409f..0x2840a9` 将 `"vbios000"` 写入栈内缓冲；最后一个字符位于 `[rbp+0x5e]`。
- `0x284648..0x284665` 调用 `_nv049785rm` 读取基础键 `vbios`，第三参数为缓冲区，第四参数为容量/实际长度变量。重定位证据：调用目标 `_nv049785rm`；键指针重定位到 `.rodata+0x4c4bc33`，对应字面值 `vbios`。
- 只有读取成功且返回长度 `n` 满足 `0x200 <= n <= C` 时，才由 `0x28467a` 进入 `0x284f88` 的编号分支。

### A.2 编号键循环

在进入编号分支时，累计偏移 `off` 初始为基础读取返回长度 `n`：

```text
request = C - off
key     = "vbios" + three-digit suffix
write   = buffer + off
read_binary(gpu, key, write, &request)
```

对应指令：

- `0x284f88..0x284f8f`：保存当前返回/偏移，并检查 suffix 是否已经为 `'9'`。
- `0x284fc0..0x284fd9`：
  - `edx = C - returned_offset`；
  - `rcx = &([rbp+0x24])` 作为长度指针；
  - `rsi = &([rbp+0x57])` 作为键名指针；
  - `rdx = buffer + off`；
  - 调用 `_nv049785rm`。
- `0x284fde..0x284fe3`：读取失败则结束当前循环。
- `0x284fa0..0x284fa8`：计算 `new_off = old_off + returned_length`，若无符号 `new_off > C` 则结束。
- `0x284faa..0x284fb4`：保存新偏移，并将 `[rbp+0x5e]` 加一。
- `0x284fb7..0x284fba`：若新 suffix 达到 `'9'`，跳到 `0x2850f7` 收尾。

因此：

1. 请求量是**剩余容量 `C-off`**，不是固定块大小，也不是递增序列；成功后通常递减。
2. suffix 只对最后一个 ASCII 字符做加一，没有十进制进位。
3. 从 `vbios000` 开始，最多请求 `vbios000` 至 `vbios008`；达到 `'9'` 时停止，因此不请求 `vbios009`。
4. 若返回零长度，`off` 可不变，静态上没有专门的 `off==C` break，下一轮可能提交零容量请求；不可据此宣称一定会继续获得数据。
5. 失败或越界时保留此前累计偏移并收尾。
6. `0x284fe5..0x284ff5` 设置对象状态并跳回 `0x284250`；`0x284254/0x28425e` 将累计长度写入对象 `+0x2f0`，将 buffer 写入对象 `+0x2e8`。

### A.3 不应误并入 chunk 循环的代码

`0x285001..0x28503e` 是另一 fallback 分支：调用 `_nv052695rm`，按长度填充 `0xff`，再调用 `_nv049845rm`，最后设置状态 `8` 并跳往 `0x284940`。它由 `0x284e1c` 路径到达，不是 `vbios000` 编号循环的延伸。

## B. cache 门控

- `0x284134` 读取对象 `+0x2e8`。
- `0x28413b..0x28413e` 测试是否为空。
- 非空路径在 `0x28414c..0x284162` 返回成功，跳过后续 `vbios`/编号 registry 读取。

可确证结论：同一对象的 `+0x2e8` cache 保持非空时，再进入该 consumer 不会重读 `vbios` 或 `vbios000..`。因此，仅修改 registry 存储不能证明会热重载。

限制：尚未解析 `rm_write_registry_binary` 内部是否会失效 cache，也未追踪其他释放/重建对象的路径；所以不能把上述结论扩大为“任何 live 写入永远不会触发重读”。

## C. per-GPU registry 与 `rm_init_adapter` 时序

源码证据：

- `nv-procfs.c:1411` 定义 `nv_procfs_add_gpu`。
- `nv-procfs.c:1426` 创建 BDF GPU 目录。
- `nv-procfs.c:1435` 创建 per-GPU `registry` proc 文件。
- `nv-pci.c:414..419` 在 PCI probe 中调用 `rm_init_private_state`；这不是 `rm_init_adapter`。
- `nv-pci.c:534` 调用 `nv_procfs_add_gpu(nvl)`。
- `nv-pci.c:537` 随后调用 `nv_parse_per_device_option_string(sp)`。
- `nv.c:1642..1656`：未设置 `NV_FLAG_OPEN` 时，`nv_open_device` 调用 `nv_start_device`。
- `nv.c:1468..1493`：`nv_start_device` 内调用 `rm_init_adapter`，成功后才设置 `NV_FLAG_OPEN`。

因此源码不支持“per-GPU registry 必须在 `rm_init_adapter` 成功后才创建”的前提，也不能由创建时序单独宣布 bootstrap 循环。

`nv-procfs.c:264..315` 的 registry open 路径只显式分配 private/stack/buffer；`318..347` 执行 `single_open` 与 PM 读锁；`350..431` 的 close 路径在 `390..391` 调用 `rm_write_registry_binary`，随后维护 registry key 名称列表。该路径没有显式调用 `nv_open_device`、`nv_start_device`、`rm_init_adapter` 或 cache invalidation。

## D. 尚未知与收尾判断

尚未知：

- `+0x158` 虚函数实际目标及容量 `C`；
- 第一次 consumer 调用的确切时机；
- `rm_write_registry_binary` 的内部生命周期/失效语义；
- 其他路径是否释放或重建 `+0x2e8` 对象；
- 后续内容、签名、板型及功能校验是否接受输入。

收尾判断：已确证二进制 registry 的基础 `vbios` 读取、有限编号拼接及对象级 cache 门控；未确证热加载机制，也未确证 V100 功能解锁可行性。按研究边界停止，不猜 setter，不做上机验证。

## E. 实测确认（2026-10-25 傍晚追加）

本节为上述静态结论的**上机验证**结果，详见 [`02-功耗墙实测.md`](02-功耗墙实测.md)。结论：**B 节的 cache 门控被完整证实**。

| §D 列出的未知 | 实测结论 |
|---|---|
| `+0x2e8` cache 保持非空时是否重读 | **确认不重读。** 同一 nvidia 模块生命周期内，第二次及以后写 `vbios` 完全无效——改内容、改大小、改格式均无任何反应（连版本号都不动） |
| 其他路径是否释放/重建 `+0x2e8` 对象 | **确认会重建。** 走完 `rmmod 全栈 → PCI remove 设备 → modprobe nvidia → 写 registry → PCI rescan` 后，该 GPU 的 adapter 对象重建，`vbios` 被重新读取，覆盖生效 |
| 第一次 consumer 调用的确切时机 | 在该 GPU 的 **adapter 初始化**路径上。因此"把设备从总线摘掉再 rescan"能在不重启的前提下重新制造这个时机 |
| 后续内容/签名/板型校验是否接受输入 | **接受，但有硬约束**：payload 必须是**从 `0x55AA` 起、剔除 `0x0A00` NVGIO 前缀**的完整镜像链（本卡为 327,680 B），且基底**必须与本卡固件同版本**。跨版本镜像只被取用版本号与板卡串，功能表退化为默认值 |

补充两条与 A 节（`vbios000` 分块）相关的实测：

- **不需要触发分块循环。** 全局 registry 写缓冲为 `NV_PROC_WRITE_BUFFER_SIZE = 512 * PAGE_SIZE = 2 MiB`，单个 `vbios` 键一次即可承载完整 327,680 B payload，未观察到需要 `vbios000..` 编号键的情形。
- 写全局文件（`nv == NULL`）落在**模块级全局表**，因此能跨越单次 `unbind/rebind` 存活；而 `rmmod` 会连同该表一起清空，这也是"重启/重载即回到物理 ROM"的原因。

另修正一处：`NVreg_ExcludedGpus` 在本机 580.178.04 上**无法**用于抢占初始化窗口——设置后 V100 仍在 `modprobe nvidia` 时被初始化。
