# Tesla V100-SXM2-16GB 时钟墙突破 —— 实测记录

**日期**：2026-10-25　**主机**：本机（工作区 `/path/to/v100-vbios-research`）
**状态**：✅ **已实测成功**。核心频率 1530 → **1785 MHz**，功耗上限同步 300 → 350 W。
**口径说明**：**1785 MHz** 是 `-lgc` 设定值 / 驱动上报上限（相对 1530 为 **+16.7%**）；
**1777 MHz** 是 43 次采样得到的**实测峰值**（相对 1530 为 **+16.1%**）。本文两个数字都出现过，
凡「实测」一律指 1777，凡「设定/上限」指 1785。
**配套**：功耗墙部分见 [`02-功耗墙实测.md`](02-功耗墙实测.md)（注入点、payload 格式、窗口技巧均在该文，本文不重复）。

## 0. 结论摘要

| 项目 | 结果 |
|---|---|
| 上报 Max Clocks | 1530 → **1912 MHz** |
| 上报 Applications Clocks | 1312 → **1800 MHz** |
| **负载下真实峰值** | 1530 → **1785 MHz**（+16.7%） |
| 功耗上限 | 300 → **350 W** |
| 实测功耗峰值 | 263 W（离上限还有 87 W） |
| 实测温度峰值 | 56 °C |
| 节流 | **全程无任何节流原因激活** |
| 是否刷写 flash | 否，内存态 |

**关键结论：`XBAR` 字段不是"惰性"的**（上游 README 的说法在本卡上不成立）；**`A0` 在本固件上完全无效**。

## 1. 字段坐标（与上游对齐验证）

上游 `Tesla-v100-vbios-research/tools/tune_core.py` 的偏移与本卡镜像**恰好差 `+0x0A00`**（即上游坐标相对 `0x55AA` 起点，本卡文件含 `0x0A00` NVGIO 前缀）：

| 用途 | 上游偏移 | 本卡（`88.00.4F.00.09`） | 初值 |
|---|---|---|---|
| A0 出厂时钟偏移（s32, kHz） | `0x33220` | **`0x33C20`** | 0 |
| GPC / Applications（P-State header） | `0x30B6E` | **`0x3156E`** | 1312，ratio 328 |
| GPC row1（PSTATE_R1） | `0x30BC0` | **`0x315C0`** | 1312，ratio 328 |
| **XBAR（Max Clocks 来源）** | `0x30B97` | **`0x31597`** | `0x85FA`（标志位 + 1530），ratio 382 |
| SYS | `0x30BE9` | **`0x315E9`** | `0x85FA`（+1530），ratio 382 |

## 2. 钳位规则

```
Max Clocks = min( XBAR , 1912 )
```

`1912` 是 `clkprog` 时钟编程表（在 Image0 代码段）的最大档位。请求高于 1912 会被**优雅钳回 1912**，不报错、不崩溃。

| 请求 XBAR | 上报 Max Clocks |
|---|---|
| 1530（原厂） | 1530 |
| 1600 | 1597 |
| 1700 | 1702 |
| 1800 | 1800 |
| 1912 | 1912 |
| **2000** | **1912（钳回）** |

> 1600→1597、1700→1702 的 ±3 MHz 抖动是固件侧的量化/取整，非写入错误，可忽略。

**`Supported Clocks` 揭示的真实机制**（`nvidia-smi -q -d SUPPORTED_CLOCKS`）：

```
Memory : 877 MHz          ← 只有一档，见 04-显存频率实测.md
  Graphics : 1912 / 1905 / 1897 / 1890 / 1882 / 1875 / 1867 / 1860 /
             1852 / 1845 / 1837 / 1830 / 1822 / 1815 / 1807 / 1800 /
             1792 / 1785 / 1777 / ...
```

每档间隔 **7.5 MHz**。实测达到的 1785、1777 都落在这张表里——**GPU 是在这张离散档位表里按电压/功耗条件择档，而不是"请求多少给多少"**。这才是"上报 1912 却只跑到 ~1785"的根本原因说明。

## 3. 两套字段的分工

| 字段 | 控制的上报项 |
|---|---|
| `0x3156E` + `0x315C0`（GPC） | **Applications / Default Applications Clocks** |
| `0x31597` + `0x315E9`（XBAR/SYS） | **Max Clocks / Max Customer Boost，以及真实可跑上限** |
| `0x31523`（ENTRY0_Q） | 需与 XBAR 保持 `= XBAR/4` 一致 |
| `0x33C20`（A0） | **本固件无效** |

单改 GPC 只动 Applications，天花板不动；单改 XBAR 则天花板与真实频率一起动。

压测工具：`../tools/stress_clock.py`（`ctypes` + `libcuda` + PTX JIT，寄存器常驻 `mma.sync.m8n8k4`，1280 block × 256 thread，CHAINS=8），采样 `clocks.sm` / `power.draw` / `temperature.gpu`。

### 第一轮：定位字段

| 变体 | 改动 | 上报 max | 上报 app | **实际峰值** | 功耗 | 温度 |
|---|---|---|---|---|---|---|
| v0_stock | 对照 | 1530 | 1312 | 1530 | 142 W | 44 °C |
| v1_xbar1600 | XBAR→1600 | **1597** | 1312 | **1597** | 161 W | 46 °C |
| v2_gpc1500 | GPC→1500 | 1530 | **1500** | 1530 | 142 W | 44 °C |

**判定**：XBAR 一动，上报与真实频率同步上升，功耗 +13% → 是真实提频，不是改显示。A0 单独改无任何反应。

### 第二轮：探上限

| 变体 | 请求 XBAR | 上报 max | **实际峰值** | 功耗 | 温度 |
|---|---|---|---|---|---|

**判定**：实际频率在 ~1780 饱和；请求 1800 以上无额外收益；1912 是硬顶。

### 第三轮：A0 是否参与

假设（后被证伪）：`Max Clocks = min(XBAR, 1912 + A0)`。

| 变体 | XBAR | A0 | 上报 max | **实际峰值** | 功耗 |

## 5. 瓶颈诊断：1780 到底被什么卡住

`../tools/diag_throttle.py` 在负载下采样 25 s（81 点）：

```
上报 max 1912 / app 1912 / 功耗上限 350 W
SM 时钟：峰 1777  中位 1755
功耗   ：峰 263 W 中位 261 W
温度   ：峰 57 °C
Performance State                      : P0
clocks_throttle_reasons.*              全部 Not Active
  Idle / Applications Clocks Setting / SW Power Cap / HW Slowdown /
  HW Thermal Slowdown / HW Power Brake Slowdown / Sync Boost /
  SW Thermal Slowdown / Display Clock Setting
```

**排除了所有 NVML 可见的限制**：

- 不是功耗上限（263 W vs 350 W，余 87 W）
- 不是温度（56 °C）
- 不是任何软件/硬件节流标志
- 已处 P0 性能状态

**结论**：限制来自固件 **V/F 档位表本身**——1780 以上那几档所需的电压，当前电压-频率曲线给不出来。这类限制 NVML 不会标记为"节流"，所以看起来"无原因"。

附带：`nvidia-smi -q -d VOLTAGE` 在本卡 + 580.178.04 上**输出为空**，NVML 不暴露电压，无法直接读电压值。

## 8. 使用与回退

```bash
# 查看
nvidia-smi -q -d POWER,CLOCK -i 1 | grep -E "Power Limit|Max Clocks|Applications"

# 立即回原厂（无需重启，一条命令）
sudo rmmod nvidia_drm nvidia_modeset nvidia_uvm nvidia && \
sudo modprobe nvidia nvidia_uvm nvidia_modeset nvidia_drm

# 重新应用（会让桌面掉约 1-2 分钟，脚本自动拉起）
sudo systemd-run --unit=v100-final --collect --no-block /bin/bash /path/to/v100-vbios-research/apply_final.sh
```

> （在 SSH 里跑还会断连、脚本可能被中断）。需要长期生效请用 `deploy/` 的 systemd 单元

## 9. 未完成

1. ~~**持久化**~~（开机自动生效）—— **已于 2026-10-26 解决**：`v100-boot-patch.service` 在开机早期
   自动执行本文的注入流程，失败回原厂、不阻塞开机（见 [`01-总览与结论.md`](01-总览与结论.md) §六）。
2. **突破 1780**——需改 VFE 电压-频率曲线。风险显著高于本文所有操作：改错是**静默计算错误**（GEMM 结果错但不报错），且 `nvidia-vbios-vix-editor` 的 `gpc_curve_slot()` 对本镜像报 `FormatError: unreviewed VFE equation kind`（库只审阅 Turing/Ampere/Ada），必须自己逆向方程编码。
3. **真实任务收益**——本文压测是寄存器常驻 MMA（263 W），不代表 GEMM/训练负载。真实任务功耗会更高，需实测确认 350 W 余量是否真被用掉、以及 +16.7% 频率能否转化为吞吐。
4. **VFE 钳位值** 1912（`0x322DF+8` 的 f32）与 `clkprog` 1912 上限的关系未验证是否为同一约束。
5. **显存频率**——已实测**硬件频率不可改，只有上报值可改**：`-lmc` 在 V100 上完全不被支持；VBIOS 里两处字段同时改成 600 后驱动确实显示 600、`Supported Clocks` 也变 600，但 `current.memory` 恒为 877、实测带宽恒为 805–809 GB/s（600 MHz 理论上限仅 614 GB/s，反证硬件未变）。第一轮（向上）四变体 + 第二轮（向下）五变体，详见 [`04-显存频率实测.md`](04-显存频率实测.md)。

6. **P38 字段已验证为惰性**——`0x38EA9` / `0x391FB`（本 ROM 原值 1530，正等于原厂 Max Clocks，上游称其为 "target clock"）在 BIT token 流中形如 `fd fa 05`（token `0xFD` + `0x05FA`）。四向测试全部无效：设 1912 → 1785、设 2000 → 1777、**设 1200 仍跑 1777（未被限住）**、原值 1530 → 1785。若它是上限字段，设 1200 必然把时钟压到 1200，故确认它既非上限也非目标值。

7. **平台侧无优化空间（已核查）**——PCIe 为 Gen3 x16（已是上限）、`intel_iommu=on iommu=pt`（开销最低的直通模式）、单路 CPU 全 NUMA0。换插槽、关 IOMMU 一类操作在本机均为零收益。

8. **350 W 是否真被用上——仍未验证**。现有全部压测最高只到 267 W，离 350 W 还有 83 W。若真实训练负载会撞到原厂 300 W 上限，则抬到 350 W 直接换来不掉频；若真实负载吃不到 300 W，则该改动在日常使用中收益有限。可用 `nvidia-smi -pl 300` vs `-pl 350` 做运行中 A/B（无需改 VBIOS、不掉桌面）。

11. **ECC 关闭不必尝试**——V100 的 HBM2 使用专用 ECC 位（sideband），不占数据带宽，预期收益约为 0，且需重启并丢失错误检测。

7. **Image0 改动可被硬件真正采纳**——本轮实测确认：把 Image0 `0x7E72` 由 877 改为 600，`clocks.sm` 真实降至 600 MHz、带宽随之掉到 488.8 GB/s。这**推翻了"只有数据镜像有效、Image0 属代码段动不得"的旧假设**。若将来要再攻 1780→1912，Image0 侧是一条未被排除的路径（尽管瓶颈仍是电压/VID）。

## 附录 A：VFE 结构解构与其余时钟域（2026-10-25 补充）

### A.1 VFE 是分段函数表，不是"频率→电压"配对表

头部 `@0x3200E`：`30 07 19 0f` → ver `0x30`，rows `25`，cols `15`。
数据起点 `0x3218F`，每槽 **24 字节**，布局为：

```
[域下界 f32] [域上界 f32] [值 f32] [系数a f32] [系数b f32] [保留 f32] + 4 字节 tag
```

实测槽位内容：

| 槽 | 偏移 | 内容 | 解读 |
|---|---|---|---|
| 0 | `0x3218F` | 域 `1025000..1068750` → `1139843.75` | **电压（µV）**：1.025–1.069 V → 1.140 V |
| 2 | `0x321BF` | `1125000` 常量 | 电压 1125 mV |
| 3 | `0x321D7` | `668750` 常量 | 电压 668.75 mV |
| **8** | `0x3224F` | `a=-2527.91, b=1.78` | **线性方程**（V↔f 斜率关系） |
| 9 | `0x32267` | `500000` 常量 | 频率 500 MHz |
| 10–12 | `0x3227F..` | `405 / 406.10 / 405` | 某固定域 |
| 13 | `0x322C7` | **`1904.47`** 常量 | 频率档（全域 `-FLT_MAX..+FLT_MAX`） |
| **14** | `0x322DF` | **`1912.00`** 常量 | **即 1912 钳位的来源** |

### A.2 关键结论

1. **`0x322E7` 的 f32 `1912.0`（slot14）就是钳位本体**。请求 XBAR > 1912 被钳回 1912，来源在此。
2. **抬高 slot14 只能改上报，改不了实际频率**——实际天花板 ~1785 由电压/VID 决定（已由"锁 1852 仍只跑 1785"证明）。
3. **"下移 VFE"在本卡上没有意义**：a) 上游用它只为补偿 A0，而 A0 已证惰性；b) 下移等于降电压，收益是省电而非提频；c) 下移 slot14 是把天花板压低，方向相反。
4. 本卡非功耗/温度受限（267 W / 57 °C），降压换不来任何频率。

### A.3 其余频率域总账

| 域 | 可否修改 | 对算力是否有用 |
|---|---|---|
| **SM / GPC** | ✅ 已改（1530 → 1785） | **就是唯一有效杠杆** |
| 显存 | ❌ 仅上报值（见显存记录） | 无 |
| **视频（555，上限 1372）** | ✅ 同类字段可改 | 仅影响 NVENC/NVDEC 编解码，不影响计算 |
| XBAR / SYS 字段 | ✅ 已写（1912） | 效果并入 SM 天花板，未见独立可观测域 |
| VFE 钳位（1904.47 / 1912） | ✅ 可改 | 仅上报 |
| VFE 电压项（1025/1069/1140/669/1125 mV 等） | ✅ 可改 | 属电压方向，已排除 |

**结论：核心之外没有剩余可捡的算力。1785 MHz 是不加压条件下的物理终点。**

### A.4 未走的两条路（明确记录，供后续参考）

| 路线 | 内容 | 为何未做 |
|---|---|---|
| 抬高 VFE slot14（如 2100） | 纯机制验证，确认钳位位置 | 无性能收益，仅为满足机制好奇 |
| L2 带宽对比（XBAR 1530 vs 1912） | 判定 XBAR 是否为独立域 | 同上；即便成立，L2 带宽（~3–4 TB/s）远高于 HBM，非瓶颈 |
