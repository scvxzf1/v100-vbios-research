**日期**：2026-10-25　**主机**：本机（工作区 `/path/to/v100-vbios-research`）

## 一、成果

| 项目 | 原厂 | 现在 | 实测收益 |
|---|---|---|---|
| 功耗上限 | 300 W | **350 W** | 高负载下不掉频（头寸余量待验，见 §七） |
| 核心频率上限 | 1530 MHz | **1785 MHz** | **算力 +15.5%**（115.9 → 133.9 TF/s，FP16 张量） |
| Applications Clocks | 1312 MHz | 1800 MHz | 支持以更高基准锁频 |
| 上报 Max Clocks | 1530 MHz | 1912 MHz | — |
| 显存频率 | 877 MHz | 877 MHz | **不可改**（仅上报值可改） |
| flash 写入 | — | **0 字节** | 零变砖风险 |

**核心判断**：`1530 MHz` 是 VBIOS 的**策略上限**，`1785 MHz` 才是这卡在**出厂电压**下的真实物理天花板。本次工作把策略限制剥掉、释放了硅片的全部余量，且未增加一毫伏电压。

**能效代价**（重要）：1785 MHz 时 0.525 TF·s⁻¹·W⁻¹，1530 MHz 时 0.835 TF·s⁻¹·W⁻¹。**性能 +15.5%，功耗 +84%**（139 → 255 W）。多卡或电源受限场景应优先选 1530。

## 二、技术路线（四步缺一不可）

```
1. 取原始固件   nvflash 5.867.0 --save      （V100 无 ROM BAR，其他方式取不到）
2. 找注入点     /proc/driver/nvidia/registry 的二进制 vbios 键
3. 卡准时机     PCI remove → modprobe → 写 → rescan（不重启即可命中，约 30 秒一轮）
4. 改对字段     基底必须与卡同版本；功耗改 row4，频率改 XBAR
```

### 2.1 注入点

```bash
{ printf 'vbios='; cat payload.bin; } > /proc/driver/nvidia/registry
```

- payload 格式：**从 `0x0A00`（`0x55AA`）起、到最后一个镜像末尾**，本卡为 **327,680 字节**
- 带 `0x0A00` NVGIO 前缀的全量 1 MiB 会被**静默忽略**
- 写全局文件（`nv == NULL`）落在模块级表，可跨 `unbind/rebind` 存活；`rmmod` 即清空

### 2.2 生效时机（每个模块生命周期只读一次）

```bash
rmmod nvidia_drm nvidia_modeset nvidia_uvm nvidia
echo 1 > /sys/bus/pci/devices/0000:04:00.0/remove
modprobe nvidia
{ printf 'vbios='; cat payload.bin; } > /proc/driver/nvidia/registry
echo 1 > /sys/bus/pci/rescan     # V100 回来并 probe → 读到覆盖
```

### 2.3 两条铁律

1. **基底必须与本卡固件同版本**（`88.00.4F.00.09`）。跨版本只吃版本号与板卡串，功能表退化为默认值。
2. **表位置从 BIT 指针动态解析**，不要硬编码 —— 换镜像偏移会变。

## 三、字段总账（本卡实测）

| 用途 | 偏移 | 初值 | 结论 |
|---|---|---|---|
| 功耗 TGP row4（min/rated/max） | `0x33489` `+2/+6/+10` | 150/300/300 W | ✅ **有效** |
| XBAR（真实频率杠杆） | `0x31597` | `0x85FA`(1530) | ✅ **有效** |
| SYS | `0x315E9` | `0x85FA`(1530) | ✅ 配合 XBAR |
| GPC / Applications | `0x3156E`、`0x315C0` | 1312 | ✅ 有效（仅上报 app 时钟） |
| ENTRY0_Q（须 = XBAR/4） | `0x31523` | 382 | ✅ 需保持一致 |
| **A0 出厂偏移** | `0x33C20` | 0 | ❌ **惰性**（+100/+200/+300 全无反应） |
| **P38** | `0x38EA9`、`0x391FB` | 1530 | ❌ **惰性**（含压到 1200 仍跑 1777 的反向验证） |
| 显存时钟（数据区） | `0x3152B` | 877 | ❌ 仅上报 |
| 显存时钟（Image0 `clkprog`） | `0x7E72` | 877 | ⚠️ 实物为 **SM 侧**字段，非显存 |
| VFE 钳位 | `0x322E7`（slot14） | f32 `1912.0` | ⚠️ 1912 钳位本体，仅上报 |
| VFE 电压项 | `0x3218F..` | 1025/1069/1140/669/1125 mV | ⚠️ 电压方向，已排除 |

> **顺带确认**：覆盖注入对 **Image0（代码段）** 的改动**会被硬件真正采纳**（把 `0x7E72` 改 600，`clocks.sm` 真的降到 600），推翻了"只有数据镜像有效"的旧假设。

## 四、否定结论清单（避免重复投入）

| 尝试 | 结果 | 原因 |
|---|---|---|
| 提高显存频率 | 只改上报值 | HBM2 单 strap，POST 阶段锁定；`-lmc` 在 V100 上完全不被支持 |
| 降低显存频率 | 同上 | `current.memory` 恒 877，带宽恒 805–809 GB/s |
| 改 A0 | 无任何反应 | 本固件惰性（上游 "Max Clocks=1912+A0" 不适用） |
| 改 P38 | 无任何反应 | 本固件惰性 |
| 锁 1852 MHz 以上 | 仍只跑 1785 | **电压/VID 硬顶**，非加速策略问题 |
| 关闭 ECC 换带宽 | 不做 | V100 HBM2 用专用 ECC 位（sideband），预期收益 ≈ 0 |
| 平台侧优化（PCIe/IOMMU） | 零收益 | 已 Gen3 x16、`iommu=pt`、单路全 NUMA0 |
| 降压超频 | 不适用 | 非功耗/温度受限（267 W / 57 °C），降压不提频反而可能压低上限 |

## 六、运行与回退

### 当前机内状态（内存态，重启即失效）

```
vbios_version        88.00.4F.00.09
power.limit          350.00 W   (min 150 / max 350)
clocks.max.sm        1912 MHz
clocks.applications  1800 MHz
clocks.current.memory 877 MHz
registry             Binary: "vbios"     ← 覆盖在位
```

### 回退

```bash
# 一条命令回原厂（无需重启）
sudo rmmod nvidia_drm nvidia_modeset nvidia_uvm nvidia && \
sudo modprobe nvidia nvidia_uvm nvidia_modeset nvidia_drm
```

### 重新应用

```bash
sudo systemd-run --unit=v100-final --collect --no-block \
  /bin/bash /path/to/v100-vbios-research/apply_final.sh
# 会让桌面掉 1-2 分钟，脚本自动恢复并保留配置
```

> 注意：`apply_final.sh` 等脚本需要卸载驱动，会使图形会话与依赖 `user@1000.service` 的进程一并结束。
> 因此统一用 `systemd-run --unit=... --collect --no-block` 提交，任务可独立跑完并自动恢复桌面。

### ⚠️ LACT 会抢改功耗上限（已修复，务必注意）

`lactd` 守护进程会按 `/etc/lact/config.yaml` 每 5 秒重放一次设置。它自动为 V100 建了条目，其中 `power_cap: 300.0` 会**把 350 W 静默改回 300 W**——表现是 `max_limit` 显示 350 但 `power.limit` 只有 300。

```yaml
# /etc/lact/config.yaml
  10DE:1DB1-10DE:1212-0000:04:00.0:
    fan_control_enabled: false
    power_cap: 350.0          # ← 原为 300.0，已改
    min_core_clock: 135
    max_core_clock: 1912      # ← 有益：等价于帮我们锁 -lgc 135,1912
```

已修改为 `350.0` 并重启 `lactd`。**若将来出现"功耗又回 300"，第一件事就是查这个文件。**
配置备份：`/etc/lact/config.yaml.bak-<时间戳>`。

### 开机自动生效（v100-boot-patch.service，已启用）

| 组件 | 路径 |
|---|---|
| systemd 单元 | `/etc/systemd/system/v100-boot-patch.service` |
| 执行脚本 | `/usr/local/sbin/v100-boot-patch.sh` |
| payload | `/etc/v100/v100_final_payload.bin`（327,680 B，sha256 `8163a67d…`） |
| 运行日志 | `/var/log/v100-boot-patch.log` |

时序：`After=systemd-udev-settle.service` → `Before=display-manager.service gdm.service`，即在任何显示管理器抢住 GPU 之前完成注入。

安全设计（**绝不阻塞开机**）：

- 所有失败路径统一走 `fail()`：rescan 恢复设备 → 重新拉起 lactd → `exit 0`
- 卡不存在时等待 **10 秒**后干净跳过，系统以原厂状态正常启动
- `TimeoutStartSec=120`，脚本最坏耗时约 10 + 15 秒
- 失败时保持原厂 300 W / 1530 MHz，功能不受影响

操作：

```bash
# 装回显卡但不重启时，手动应用一次
sudo /usr/local/sbin/v100-boot-patch.sh && tail -5 /var/log/v100-boot-patch.log

# 查看开机是否成功（应出现 "成功: vbios=88.00.4F.00.09  max_limit=350.00W  max_sm=1912MHz"）
cat /var/log/v100-boot-patch.log

# 关闭开机自动注入（立即恢复到原厂行为）
sudo systemctl disable --now v100-boot-patch.service

# 重新启用
sudo systemctl enable v100-boot-patch.service
```

> ⚠️ 该单元会 `systemctl stop lactd`（LACT 守护进程握住 `/dev/nvidia*` 会导致驱动无法卸载），结束时再拉起。若改动 LACT 配置，注意其 `power_cap` 必须保持 `350.0`，否则会把 350 W 改回 300 W。

### 能效档位切换（运行中，零风险）

```bash
sudo nvidia-smi -i 1 -lgc 1530,1530   # 能效模式（0.835 TF/s/W）
sudo nvidia-smi -i 1 -rgc             # 解除，回到 1785
```

## 七、遗留项

1. ~~**持久化未做**~~ —— **已于 2026-10-26 01:56 完成**。开机单元 `v100-boot-patch.service` 已启用，每次开机在显示管理器启动前自动执行 §2.2 的窗口流程；任何环节失败都会回退原厂状态且不阻塞开机。详见 §六「开机自动生效」。
2. **350 W 是否真被用上——未验证**。全部压测最高仅 267 W，离 350 W 尚差 83 W。可用 `nvidia-smi -pl 300` vs `-pl 350` 做运行中 A/B（零风险、不掉桌面）。若真实训练负载会撞到原厂 300 W 上限，则此项改动直接换来不掉频；否则日常收益有限。
3. **真实 GEMM 收益未测**——本机无 cuBLAS / torch / nvcc，实测的是手写 PTX 寄存器常驻张量核心内核（无访存），+15.5% 是最好情况；真实 GEMM 预计 +8~12%。
4. **应用层优化未展开**——纯计算路径已达 1777 MHz 理论峰值的 92%，剩余空间在访存与数据管线（张量核心利用率、cuBLAS 选型、pinned memory + 多流、batch size）。
5. **显存真降频只能靠刷写**——需配套改 PLL 分频与训练时序，训练失败会 POST 不过，须编程器救援。**不建议**。
