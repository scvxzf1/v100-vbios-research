# Tesla V100-SXM2-16GB 显存频率 —— 实测记录（结论：硬件频率不可改，仅上报值可改）

**日期**：2026-10-25　**主机**：本机（工作区 `/path/to/v100-vbios-research`）
**状态**：❌ **显存硬件频率无法通过 VBIOS 覆盖修改**。可以改的只有驱动的"上报值"。
**配套**：注入点与 payload 格式见 [`02-功耗墙实测.md`](02-功耗墙实测.md)；核心频率见 [`03-时钟墙实测.md`](03-时钟墙实测.md)。

---

## 0. 结论

| 项目 | 结果 |
|---|---|
| 驱动显存时钟控制通道（`nvidia-smi -lmc`） | **完全不被支持**（连设成当前值都报错） |
| VBIOS 上报值 | **可以改成任意数字**（`max.memory` 与 `Supported Clocks` 均随之改变） |
| 硬件实际频率 | **始终 877 MHz 不变**（`current.memory` 恒 877，实测带宽恒定 805–809 GB/s） |
| 判据 | 带宽。若真降频到 600，理论带宽上限只有 614 GB/s，而实测 809 → 硬件未变 |

**一句话**：V100 的 HBM2 时钟在 POST 阶段由 strap 锁定，VBIOS 只向驱动提供"报告用"的数值。我们可以随意改这个数值，但改不动硅片。

## 1. 测量方法（地面真值）

`../tools/mem_bw.py`：CUDA driver API，两块 256 MiB 缓冲做 `cuMemcpyDtoD_v2`，带宽 = `2 × bytes / time`（读 + 写）。

```
原厂基线: 804.7 / 805.4 / 809.3 / 805.8 GB/s   （理论 900，达成约 90%）
```

**判据**：显存频率若真变化，带宽必须按比例变化。只有上报值变化而带宽不动，即为假。

---

## 2. 驱动层：根本没有控制通道

```bash
$ nvidia-smi -i 1 -lmc 877,877
Setting locked Memory clocks is not supported for GPU 00000000:04:00.0.

$ nvidia-smi -i 1 -lmc 405,405
Setting locked Memory clocks is not supported for GPU 00000000:04:00.0.

$ nvidia-smi -q -d SUPPORTED_CLOCKS -i 1
        Memory                                         : 877 MHz      ← 唯一条目
```

注意第一条：**连设成它自己的当前值都被拒绝**。这不是"值超出允许范围"，而是驱动里没有实现显存时钟控制。与 SM 时钟形成鲜明对比——`-lgc` 任意可用。

## 3. 第一轮（向上方向，基底=已生效的 350 W + XBAR 1912 + GPC 1800）

| 变体 | 改动 | `max.memory` | 支持档位 | **实际带宽** | ECC |
|---|---|---|---|---|---|
| `m0_base` | 对照 | 877 | 877 | 809.2 GB/s | 0 |
| `m1_1000_min` | `0x3152B` → 1000（+比率 219→250） | **877** | 877 | 808.5 GB/s | 0 |
| `m2_1000_full` | 再加 `0x3152D`/`0x31576` → 19682 | **877** | 877 | 806.6 GB/s | 0 |
| `m3_1126` | 激进 +28%：→1126 / 22162 | **877** | 877 | 810.7 GB/s | 0 |

单改数据区字段：**连上报值都不变**。

## 4. 第二轮（向下方向，基底=纯原厂，只动显存）—— 关键结果

| 变体 | 改动 | `current.memory` | `max.memory` | 支持档位 | **实际带宽** | `clocks.sm` |
|---|---|---|---|---|---|---|
| `d0_stock` | 对照 | **877** | 877 | 877 | **804.7 GB/s** | 1312 |
| `d1_data600` | 只改数据区 `0x3152B` → 600 | **877** | 877 | 877 | 805.4 GB/s | 1312 |
| `d2_code600` | 只改 Image0 `0x7E72` → 600 | **877** | 877 | 877 | **488.8 GB/s** | **600** ⚠️ |
| `d3_both600` | 两处都改 | **877** | **600** | **600** | **809.3 GB/s** | 1312 |
| `d4_all600` | 再加 Image1 两份副本 `0x1154D`/`0x1C206` | **877** | **600** | **600** | 805.8 GB/s | 1312 |

### 4.1 上报值可以随便改，硬件不变

`d3`/`d4` 让驱动显示 `600 MHz`，`Supported Clocks` 也变成 600——但带宽 809 / 806 GB/s，与对照的 805 完全一致。

数学上不可能是真的：600 MHz 时 HBM2 理论带宽 `600 × 2 × 512 = 614 GB/s`，实测 809 已超出该上限。

### 4.2 最硬的证据：`current.memory` 恒为 877

NVML 的 `current` 读硬件实况，`max` 读 VBIOS 表值。五个变体里 `current.memory` **一次都没动过**，只有 `max` 在 d3/d4 跟着改了。

```
硬件真值   →  877（不可动）
VBIOS 表值 →  任意数字（纯上报）
```

### 4.3 存在交叉校验：必须两处同时改才生效于上报

`d1`（只改数据区）→ `max` 仍 877；`d2`（只改代码区）→ `max` 仍 877；`d3`（两处一致）→ `max` 变 600。

这解释了第一轮"单改数据字段毫无反应"的原因：**两处不一致时驱动退回硬件值**。

## 5. 重要更正：`0x7E72` 不是显存记录，而是 SM 侧

原记录 §4 曾把 Image0 `clkprog` 里 `0x7E63` 那条（`clock=877`）当作显存时钟记录。**这个判断是错的。**

`d2` 只把 `0x7E72` 从 877 改成 600，结果是：

```
clocks.sm        1312 → 600 MHz     （真实下降，不是上报值）
实际带宽    804.7 → 488.8 GB/s     （SM 发不动访存指令）
```

所以该字段影响的是 **SM 侧时钟**，与显存无关。

**顺带一个更有价值的推论**：覆盖注入对 **Image0（代码段）的改动是被硬件真正采纳的**。此前"Image0 动不得、只有数据镜像才有效"的假设不成立——这条对后续任何 Image0 方向的尝试都适用。

`clkprog` 区域（`0x7E2D` 一带）的实际记录内容：

| 偏移 | N | YY | 值 | W |
|---|---|---|---|---|
| `0x07E2D` | 24 | `0x01` | 1080 | `0x0c` |
| `0x07E48` | 28 | `0x01` | 1325 | `0x0c` |
| `0x07E63` | 32 | `0x81` | 877（→ **SM 侧**） | `0x0a` |
| `0x07E8A` | 41 | `0xa0` | 1912 | `0xff` |

这四个值（1080/1325/877/1912）是**按时钟域各一条**，不是频率阶梯；`N`/`YY`/`W` 是配套的 PLL/时序参数，语义未解。

## 6. 为什么硬件频率动不了

**显存 PLL 在 POST 阶段按 strap 锁定**，而本方案的内存覆盖注入发生在 POST 之后。覆盖能替换驱动"看到"的 VBIOS 表，但改不了早已在硬件里定死的分频。

**推论**：若改为**刷写 flash 并重启**，该改动理论上可能在 POST 阶段生效。

代价与风险：

- 显存换频必须同步修改 PLL 分频与训练参数（时序），只改频率数字大概率训练失败
- 训练失败 = **卡可能直接 POST 不过**，只能拆机用编程器恢复
- 虽已有 `v100_original.rom` 备份 + 编程器可救，但这是全部操作中唯一存在真实变砖风险的动作

**结论：除非明确需要且接受该风险，否则不建议走刷写路线。**

## 7. 替代方案：如果目的是省电/降热

显存不是有效的杠杆（其功耗占比小，且动不了）。可控的杠杆在 SM 侧，干净且随时可逆：

```bash
sudo nvidia-smi -i 1 -lgc 900,900     # SM 降频，功耗立降
sudo nvidia-smi -i 1 -rgc             # 解除
sudo nvidia-smi -i 1 -pl 200          # 功耗上限（需先把 min 从 150 W 解锁）
```

参考量级（见时钟墙记录 A/B）：SM 1530 MHz 时 138.8 W / 0.835 TF·s⁻¹·W⁻¹，1785 MHz 时 255.3 W / 0.525 TF·s⁻¹·W⁻¹。

## 9. 附：两处顺带确认

1. **SM 档位表**：`Supported Clocks → Graphics` 为 `1912 / 1905 / 1897 / … / 1785 / 1777`，每档间隔 **7.5 MHz**，GPU 在离散档位表中择档而非"请求多少给多少"。
2. **显存档位表**：`Supported Clocks → Memory` 只有 **一条**（877），受 VBIOS 上报值影响（d3/d4 下变为 600），但不反映硬件。
